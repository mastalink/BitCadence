CONCLUSION (corrected after reading the result rather than predicting it):

Readiness DOES surface this. `SweepResult.failing` carries per-run tick errors
as well as blocked/failed runs, so /readyz names s06a-11-rootmismatch in
checks.score_sweep.failing_runs even though the run's own status is still
'running'. The gateway stays `ok: true` - correctly, because the sweep itself
is healthy; it is one run that is broken, and the run is named.

What remains is a configuration trap, not a blind spot:

  `mco score start` resolves --db and --artifact-root from Path.home() and
  never reads MCO_SCORE_DB / MCO_SCORE_ARTIFACT_ROOT, which is where the
  gateway sweep reads them. Point the gateway at a non-default artifact root
  and the documented CLI invocation silently starts runs the gateway will
  refuse forever with "Run artifact root mismatch".

This is not theoretical: it is exactly what happened to this packet's first
baseline attempt, and it cost a full setup cycle. The run IS named in
failing_runs, so an operator watching /readyz would catch it - but the error
string names the symptom, not the cause, and nothing points at the two
different config sources. Recommended follow-up in the report.
