BITCADENCE / USER GUIDE

Complete CLI reference

Use bitcadence for everyday work. mco is a supported compatibility name for the same command tree: every path below works with either executable. The desktop entry point is separate: bitcadence-desktop launches the native desktop app; its pages are covered by the GUI reference.

This reference covers every registered command and group recursively, every positional argument, option spelling, parser default, repeatable/variadic parameter, prompt and declared range/path constraint. It includes generated completion/help options and the hidden compatibility option gui --flow. Defaults are parser defaults; configuration or the implementation may resolve unset values at runtime. ~ means your home directory; .mco, MCO_ and the Python package mco remain supported compatibility names.

Read this first

  • Run bitcadence in an interactive terminal for the menu. In scripts/non-interactive use it prints help and exits 2; bitcadence --no-menu deliberately prints help and exits 0. MCO_NO_MENU=1 also disables the menu.
  • Put global options before the command: bitcadence --debug status. Group options belong before their subcommand, for example bitcadence helpers --json.
  • Add --help to a specific command to inspect it safely, for example bitcadence score start --help. Except for the transparent advanced forwarder, help exits before operational callbacks. No credentials or production commands were executed to produce this reference.
  • Examples containing JOB_ID, INSTANCE_ID, WORKER_NAME, SCHEDULE_NAME, EXCHANGE_ID, CLIENT_WORKTREE, or file names require your actual values/files. They describe intended operations; they are not a script to run from top to bottom. Commands that change state say so in their expected result/recovery notes. For effectful/restricted operations the example may intentionally stop at help.
  • --yes only exists where listed. It skips that command's questions; it does not add permission. A daemon running, a job submitted, or an exit-0 policy reply does not prove the work succeeded.
  • Most failures exit 1; syntax errors typically exit 2. Important exceptions are documented per command (empty results/missing schedule or fleet config/advisory verdicts). Do not infer success from exit code alone.

  • mco agents — List all registered agents and their current online presence status.

  • mco connectors — List configured enterprise connectors and their health (via the gateway).
  • mco deregister — Remove an agent registration. Its token stops working immediately.
  • mco doctor — Diagnose an install end to end: Python, config, secret store, database, gateway, agents, vendor CLIs. Exit code 1 if anything is broken.
  • mco duplicates — List other jobs that look like the same work as this one.
  • mco edition — Show the active edition (community/team/enterprise) and feature matrix.

  • mco launch — Fire a launcher right now, by name.

  • mco reassign — Clone a failed job onto a new target, link both rows, and archive the old one (approver-role token).
  • mco recall — Recall the most relevant Drumline shared-context entries.
  • mco register — Register a new client agent, generating a secure access token.
  • mco reject — Reject a job paused at the human-in-the-loop gate (terminal).
  • mco remember — Append an entry to the Drumline shared context.
  • mco reset-token — Rotate an agent's access token. The old token stops working immediately.
  • mco restart — Restart the background gateway (stop if running, then start).
  • mco restore-fence — After a DB restore, pause work and invalidate every pre-restore claim.
  • mco resume — Resume after a pause.
  • mco retry — Re-queue a failed or rejected job back to pending (approver-role token).
  • mco schedule — Schedules and loops: what work gets created, and when.
    • mco schedule add — Add a schedule by asking what, how often and what time.
    • mco schedule disable — Disable a schedule or loop, leaving its definition and history intact.
    • mco schedule enable — Enable a schedule or loop (without hand-editing YAML).
    • mco schedule init — Write a starter ~/.mco/schedules.yaml.
    • mco schedule list — Show every schedule and loop with its next fire time.
    • mco schedule off — Turn a schedule off.
    • mco schedule on — Turn a schedule on.
    • mco schedule reset — Clear a schedule's run history so a finished loop can run again.
    • mco schedule run — Run the scheduler in the foreground, ticking until interrupted.
    • mco schedule tick — Run one scheduler pass (what mco schedule run does on a timer).
  • mco score — Run a Score: start, advance and inspect a conductor run.
    • mco score deliver — Bundle code, tests, README, reviews and a DRAFT client message (never sent).
    • mco score grant-local — Issue a locally auditable, interactive Score grant on Windows SQLite only.
    • mco score intake — Draft a SCOPE from a client brief (with guardrail flags), or approve a clean scope into a Score.
    • mco score list — Runs in this conductor database.
    • mco score scaffold — Turn a plain-language brief into a validated Score with build, review, and two fix attempts per step.
    • mco score start — Initialize a run. Safe to repeat: identical policy and identities resume it.
    • mco score status — Where the run actually is: per task, per phase, with the last events.
    • mco score tick — Advance the run: plan what can start, dispatch it, accept finished work.
  • mco send — Drop a job into an agent's dropbox from the terminal.
  • mco serve — Start the BitCadence FastAPI WebSocket/REST API Server.
  • mco service — Run BitCadence processes as boot-persistent OS services.
    • mco service install — Install the gateway as an OS service that starts on boot/login.
    • mco service install-scheduler — Install the schedule/loop scheduler as a boot-persistent OS service.
    • mco service install-waker — Install a self-restarting waker service for one role/instance.
    • mco service logs — Tail a service log file.
    • mco service restart — Restart the boot-persistent gateway service.
    • mco service status — Show installed BitCadence services, or one selected service.
    • mco service uninstall — Remove the boot-persistent service (does not stop a running gateway).
  • mco settings — View or change gateway settings. With nothing else, a plain summary.
  • mco setup — Configure BitCadence - a guided walkthrough or a jump-anywhere settings menu.
  • mco start — Start BitCadence quietly in the background (the pair of 'mco stop').
  • mco status — Plain summary: what needs you, what's running, any problems.
  • mco stop — Stop a running BitCadence gateway (by port).
  • mco sync — Pull open platform objects (incidents/problems) onto the job board.
  • mco tail — Live-tail a filtered mailbox feed from the gateway broadcast socket.
  • mco tray — Status light and a door into the console (Windows tray / macOS menu bar / Linux AppIndicator).
  • mco unarchive — Undo archive.
  • mco upgrade — Apply schema migrations to the configured backend.
  • mco wake — Wake a local worker command when this agent's inbox has pending jobs.
  • mco watch — Live-tail job events from the gateway's broadcast feed (Ctrl-C to stop).
  • mco workflow — Submit a declarative YAML workflow (DAG of jobs) to the Job Board.

Shared recovery

For gateway/credential failures, inspect bitcadence status --details and bitcadence doctor; check the configured gateway and the exact caller identity. An authorization failure needs an authorized operator, not a different worker's token. Read the specific diagnostic before using an effectful repair/restart. For continuous foreground commands use Ctrl+C to stop observing/driving that process.
